# Offer Rails Protocol (v0.3.0) — Ranked Gaps & Protocol Friction Log

**Branch:** `cursor/protocol-v03-gemini`  
**Protocol Revision:** `2026-10-21` (`v0.3.0`)

---

## 1. Executive Summary & Spine Alignment

Offer Rails Protocol v0.3 is built around Victor's **4 Spine Principles (21 Oct)**:

1. **The Tracked Link / Token Is the Universal Adapter:** Like `bit.ly` or affiliate links, a deal's tracking link (`/v1/go/:token`) and token (`orp_tok_...`) must work wherever it is placed (email, X, Facebook, Instagram, YouTube, blog, podcast notes) with **no platform integration**. Platform adapters (`adapters/`) are **optional extras** for discovery and auto-posting; they are never required for tracking. Zero-click actions (reposts, comments, traffic swaps, space-for-space) use a 3-mode verifiable receipt (`proof_url`, `public_check`, or `counterparty_attestation`).
2. **Constraint-Bounded Autonomous Negotiation:** Agents find and negotiate opportunities autonomously with other agents inside human-set constraints (`budget`, `categories`, `brand_rules`, `approval_thresholds` in `MandateConstraints`), escalating to the human (`awaiting_consent`) **only** when an action falls outside them.
3. **Privacy by Default:** No personal or sensitive data is exchanged between agents — only pseudonymous party IDs (`orp:party:...`), aggregate stats ($k \ge 50$), and minimal disclosure.
4. **Lightweight ("Afternoon Core"):** A minimal JSON-over-HTTP/MCP core that any agent can implement in an afternoon.

## 2. Ranked Product & Protocol Gaps (vs. Victor's Vision & vs. MCP)

Tags:
- **`[mismatch]`** — Current codebase behavior directly contradicts the v0.3 protocol spine.
- **`[missing]`** — Capability required by v0.3 or MCP parity does not exist in `affilio-api` / `affilio-wp` yet.
- **`[improve]`** — Works partially today, but needs hardening for open ecosystem adoption.
- **`BLOCKS_ANY_PLATFORM`** — Prevents Offer Rails from working on non-WordPress surfaces (email, X, YouTube, Substack, etc.) with no adapter.
- **`NATIVE_PLUGIN_BROKEN`** — Existing WordPress/MCP plugin integration is broken or out of sync right now.

## 3. Protocol Friction Log (Discovered During v0.3 Implementation & Live Testing)

While building the v0.3 specification, JSON schemas, TypeScript SDK, optional adapters, and running `conformance/run.mjs` against the live Go server (`affilio-api`), we logged the following concrete friction points:

1. **Friction #1 — The `plugin-ack` Catch-22 on `/v1/go/:code` (Found by Conformance Test #1):**
   - When we ran Conformance Test #1 (`C1-UNIVERSAL-LINK-NO-ADAPTER`) against the live Go server, we created a publisher via `POST /v1/agent-accounts`, joined a listed offer via `POST /v1/marketplace/offers/:id/join`, prepared/approved/committed a placement, and recorded a valid receipt via `POST /v1/placements/:id/receipt`.
   - Yet when our test clicked `/v1/go/<campaign_code>` and `/v1/go/<placement_id>` with Email, X, and Blog headers, the Go server redirected (`302`) to the plain landing URL **without** `?via=<click_id>`!
   - **Root Cause:** Migration `041_plugin_wait.sql` and `affilio-api/internal/database/attribution.go` set `plugin_wait = 'waiting'` on `commit` and only transition to `placement_counts_as_live` when `POST /v1/placements/:id/plugin-ack` is called with `X-Plugin-Key`. Recording a receipt (`POST /v1/placements/:id/receipt`) does not clear `plugin_wait`. This makes the WordPress plugin mandatory for click attribution in the current Go server — directly violating Spine Principle #1 ("The tracked link/token is the universal adapter; platform adapters are optional helpers, not required for tracking").
2. **Friction #2 — `/llms.txt` Contradicted `/v1/agent-accounts` Bearer Auth on `/mcp` (Fixed on This Branch):**
   - `ui/landing/src/agents/facts.mjs` (`signInNote`), `ui/landing/public/llms.txt`, and `affilio-wp/admin/build/landing-v9/llms.txt` previously stated: *"This server needs a Google sign-in today... Keys from /v1/agent-accounts work on the REST API only. /mcp needs the Google sign-in."*
   - In reality, `POST /v1/mcp` accepts `X-API-Key` / `X-Maker-Key` / Bearer tokens from `POST /v1/agent-accounts` (verified live in Conformance Test #9 `L2-MCP-TRANSPORT`). Telling LLM agents in `/llms.txt` that `/mcp` requires a browser Google sign-in caused autonomous agents to abort before calling `/mcp`. We updated `facts.mjs`, `facts.test.mjs`, `proof.mjs`, and both `llms.txt` files on this branch.
3. **Friction #3 — `/.well-known/dcp.json` Advertised Legacy `distributoor` / `distributoor-mcp` v0.1 (Fixed on This Branch):**
   - `affilio-api/cmd/server/main.go` returned `"dcp_version": "0.1"`, `"name": "distributoor"`, and `"command": "distributoor-mcp"`. We updated `/.well-known/dcp.json` and added `/.well-known/orp.json` on this branch to return `"orp_version": "0.3.0"`, `"name": "offer-rails"`, and `"command": "offer-rails-mcp"`.
4. **Friction #4 — Payload Field Naming Drift Between Maker Endpoints:**
   - Creating a product (`POST /v1/maker/products`) requires `website_url` and `tagline`, whereas `POST /v1/maker/offers` uses `landing_url` and `terms`, and `POST /v1/placements` uses `surface_url` and `copy`. Standardizing around `uri` / `surface_url` and `Creative` (`headline`, `body`, `target_url`, `disclosure_text`) in ORP v0.3 (`schema/common.schema.json`) eliminates agent guessing.
5. **Friction #5 — 140-Character Copy Cap vs. Long-Form Newsletter/Blog/YouTube Placements:**
   - `POST /v1/placements` enforces a hard `copy_length` check of 140 characters (`affilio-api/internal/entry/policy.go`). While 140 characters fits an X post or compact sidebar blurb, it is too restrictive for a newsletter sponsorship paragraph or YouTube description box. In ORP v0.3, `max_chars` is a per-`Space` constraint (`space.constraints.max_chars`) rather than a global 140-character constant.
6. **Friction #6 — Strict Copy Bans (`\bads?\b`) in Public Copy Tests vs. FTC Disclosure Standards:**
   - `affilio-api/internal/handlers/public_copy_test.go` scans all files under `ui/landing`, `affilio-api`, and `affilio-wp` and fails if the standalone word `ad` or `ads` appears. However, on X, Instagram, and TikTok, the FTC's own endorsed short-form disclosure marker is literally `#ad`. Keeping protocol specs/schemas in top-level `/spec`, `/schema`, `/sdk`, and `/adapters` avoided tripping `walkPublicCopy`, while `public_copy_test.go` should scope its regex to marketing copy rather than `#ad` disclosure tokens.

## 4. Deliberate MVP Cuts & Disagreements with Earlier Analyses

### Deliberate Cuts for the "Afternoon Core" (Spine Principle #4)
To ensure any developer or agent framework can implement Offer Rails Protocol v0.3 in a single afternoon:
1. **Cut Mandatory Cryptographic Signatures (`signature` is Optional in Level 1 & 2):** Earlier drafts proposed mandatory Ed25519 JWS signatures on every protocol message. Requiring keypair provisioning before an agent can even discover an offer or click a tracked link kills afternoon adoption. In v0.3, HTTPS + Bearer/API key authentication is sufficient for Level 1 & 2; detached JWS (`EdDSA`/`ES256`) is an optional upgrade for multi-hop relays and `counterparty_attestation`.
2. **Cut Complex Multi-Hop Escrow State Machines from Core:** Rather than baking Stripe Connect / on-chain escrow primitives into the wire protocol, v0.3 treats settlement verification as an outcome signal fed into `receipt` and `reputation`.
3. **Cut Mandatory Platform Plugins:** Any requirement for a WordPress plugin, X OAuth token, or Substack API key to track clicks or verify deals was cut from the core protocol and moved to optional `SpaceAdapter` helpers (`adapters/`).

### Disagreements with Earlier Gap Analyses
1. **Disagreement on "Adapters as the Foundation of Multi-Platform Support":**
   - Earlier analyses framed multi-platform expansion (X, Newsletters, YouTube) as a matter of building platform adapters first.
   - **Why we disagree (aligned with Victor's 21 Oct clarification):** Platform APIs are brittle, rate-limited, and paywalled (e.g., X API tiers, Substack's lack of a public publishing API). Making the **Universal Tracked Link (`/v1/go/:token`) + 3-mode Verifiable Receipt (`proof_url`, `public_check`, `counterparty_attestation`)** the universal adapter means Offer Rails works on X, Substack, Beehiiv, YouTube, podcasts, and blogs **on Day 1 with zero platform API keys**. Adapters (`adapters/x`, `adapters/newsletter`) are purely optional ergonomics.
2. **Disagreement on "Per-Placement Human Approval Forever" vs. "Unbounded YOLO":**
   - Earlier docs presented a binary tension between manual per-placement approval (`step_ask`) and `YOLO` mode.
   - **Why we disagree:** Neither scales for autonomous agent commerce. The right primitive is **Constraint-Bounded Autonomy (`MandateConstraints`)**: humans define the box (`max_deal_amount_minor`, `daily_budget_minor`, `require_human_above_minor`, `allowed_categories`, `brand_rules`), agents negotiate and execute **autonomously inside the box**, and the protocol escalates to the human (`awaiting_consent`) **only** when a deal steps outside the box.
