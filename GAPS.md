## 1. Executive Summary & The 21 Oct 12:26 Vision Spine

**Offer Rails** is the platform-agnostic, agent-agnostic, agent-oriented way to solve **any online growth work** — **traffic, engagement, monetization, clients** — for any digital product or content:

1. **Inline Mid-Task Suggestion by Any Content-Writing Agent (1 Step, Zero Signup):** Any AI that writes content for someone (blog post, X/LinkedIn thread, newsletter issue, YouTube description, docs page) can call Offer Rails mid-task in **one step** (`POST /v1/orp/inline-suggest` or `discover` with `mode: "inline_suggest"`) with **no account, no email, and no website signup**, and suggest inline: *"You can monetize this post (or swap traffic / links), want to test it?"* with a ready-to-paste tracked link (`/v1/go/:token`) and disclosure.
2. **Direct Agent-to-Agent Negotiation Replacing GTM Bots & Cold Email (`C2-NO-EMAIL-NO-SIGNUP`):** Agents **never email humans** and **never fill out website signup forms**. They negotiate directly with counterparty agents over the protocol at agent speed across **five canonical growth deal types**:
   - **`affiliate`** (monetization / clients)
   - **`cross_sell_upsell`** (clients / monetization)
   - **`link_exchange`** (traffic / SEO authority)
   - **`traffic_swap`** (traffic / audience growth)
   - **`repost_retweet`** (engagement / reach)
3. **The Tracked Link / Token Is the Universal Adapter (`C1-UNIVERSAL-LINK-NO-ADAPTER`):** A deal's tracking link (`/v1/go/:token`, forwarding `?via=<click_id>` and optional `ref` alias) and token (`orp_tok_...`) work wherever placed (email, X, Facebook, Instagram, YouTube, blog, podcast notes, in-app modals) with **no platform integration**. Platform adapters (`adapters/`) are **optional extras** for discovery and auto-posting; they are never required for tracking.
4. **Constraint-Bounded Autonomy & Zero PII:** Agents negotiate and execute autonomously inside human-set `MandateConstraints` (`budget`, `categories`, `allowed_deal_types`, `brand_rules`, `approval_thresholds`), escalating to the human (`awaiting_consent`) **only** when outside them, with **zero PII** (pseudonymous `orp:party:...` URIs and $k \ge 50$ aggregate audience stats).

## 3. Deep Dive: Site Keeper's Three Operational Findings

During live operational testing, **Site Keeper** identified three concrete blockers in `affilio-api` that impede autonomous agent testing, attribution across ecosystems, and agent-led analytics. Below is the exact code trace and v0.3 specification resolution for each finding:

### Finding 1: No Sanctioned Way to List an Offer for Private Tests Without a Public `https` Site (`GAP-05`)
- **Exact Codebase Locations:**
  - `affilio-api/internal/handlers/offers.go:187-260` (`CreateOffer`) and `368-374` (`SubmitOffer`)
  - `affilio-api/internal/handlers/listing_review.go:38-68` (`validateOfferURL`) and `149-199` (`fetchOfferHead`)
  - `affilio-api/internal/handlers/redirects.go:94,191` (`demoGoCode = "demo"`, hardcoded to `https://example.com/?demo=1`)
- **What Happens Today:**
  1. When a maker or agent calls `POST /v1/maker/offers` or `POST /v1/maker/offers/:id/submit`, `validateOfferURL` requires `https://` and calls `validatePublicTargetURL(rawURL)`, which resolves DNS and blocks `localhost`, `127.0.0.1`, private RFC1918 ranges, and non-routable test domains.
  2. Next, `SubmitOffer` runs `fetchOfferHead(ctx, landingURL)` to perform a live HTTP `HEAD`/`GET` against the public internet and runs `claims.Check(...)` (`PageClaimChecker` or `StubClaimChecker`). If the maker is not manually marked `trusted` by an admin (`POST /v1/offer-review/makers/:id/trust`) or has no live public `https` page with matching pricing/terms copy, the offer is held in `status = 'submitted'` (`review_reason = 'head'` or `'claims'`) and **cannot be joined or tested by a publisher agent**.
  3. While `GET /v1/go/demo` exists (`redirects.go:191`), it is a static no-op redirect to `https://example.com/?demo=1` that cannot be configured per offer, joined, or used to test end-to-end placement receipts.
- **ORP v0.3 Fix (`spec/architecture.md` §2.2, `schema/common.schema.json`, `schema/discover.schema.json`):**
  - Introduce `"private_test"` as a first-class value in `visibility_pools` (`"public" | "verified_only" | "allowlist" | "private_test"`).
  - Submitting an offer with `visibility_pool: "private_test"` (or `test_only: true`) transitions it immediately to `status = "listed_private_test"` **without** requiring a live internet `fetchOfferHead` or `PageClaimChecker` scrape, and allows `https://example.invalid/...` or `http://localhost:...` sandbox targets.
  - Private test offers are invisible in public marketplace discovery (`visibility_pool: "public"`) and are only discoverable/joinable by the owning maker key or explicitly allowlisted test agent keys, with all resulting clicks/conversions tagged `click_class = "test"`.

### Finding 2: No Per-Source Click Digest Readable with an Agent Key (`GAP-06`)
- **Exact Codebase Locations:**
  - `affilio-api/internal/handlers/agent_account.go:125-190` (`GetDigest` for `/v1/account/digest`) and `392-401` (`queryClicksBySource`)
  - `affilio-api/internal/handlers/agent_entry.go:1073-1185` (`GetPublisherDigest` for `/v1/digest`) and `2376-2456` (`GetMakerDigest` for `/v1/maker/digest`)
  - `affilio-api/cmd/server/main.go:530,583,853` (Route middleware wiring)
- **What Happens Today:**
  1. The SQL query `queryClicksBySource` (`SELECT COALESCE(NULLIF(source, ''), 'none') AS source, COUNT(*) ... GROUP BY 1`) is only called inside `AgentAccountHandler.GetDigest` (`GET /v1/account/digest`).
  2. `GET /v1/account/digest` is gated by `requireAccountScope`, which requires an owner-level account key (`oc_acct_...`) and explicitly rejects agent keys (`X-API-Key`, `X-Maker-Key`, or Bearer `oc_pub_...` / `oc_mkr_...`) with `HTTP 403 {"error": "account scope required"}` (verified live in `conformance/run.mjs` Check #2).
  3. Conversely, the two digest endpoints that **do** accept agent keys — `GET /v1/digest` (publisher agent key) and `GET /v1/maker/digest` (maker agent key) — only return top-level `paid_clicks` / `SelectionSummary` and **never call `queryClicksBySource`**.
  4. As a result, an autonomous agent testing multiple channels, placements, or `?via=`/`?ref=` sources has no way to read its own per-source click breakdown (`clicks_by_source`) with its agent key.
- **ORP v0.3 Fix (`spec/architecture.md` §2.3):**
  - Return `clicks_by_source` (and `verified_visits_by_source` for `traffic_swap` deals) directly in `GET /v1/digest` (authenticated with `X-API-Key` or publisher Bearer key) and `GET /v1/maker/digest` (authenticated with `X-Maker-Key` or maker Bearer key), scoped to that agent's site or maker ID.

### Finding 3: Only a `via` Param with No Optional `ref` Alias (`GAP-07`)
- **Exact Codebase Locations:**
  - `affilio-api/internal/handlers/offers.go:73` (`refParam := "via"` hardcoded in `CreateOffer`)
  - `affilio-api/internal/handlers/redirects.go:158-167` (`inboundViaFromQuery` only reads `c.Query("via")`) and `269,289,323` (`appendViaParam`)
  - `affilio-api/internal/handlers/go_privacy.go:47` (`cleanGoQuery` strips all query parameters except `"via"`)
  - `affilio-api/internal/database/attribution.go:120` (`COALESCE(NULLIF(o.ref_param, ''), 'via')`)
- **What Happens Today:**
  1. Even though the `offers` table has a `ref_param` column (`attribution.go:120`), `CreateOffer` in `handlers/offers.go:73` hardcodes `refParam := "via"` and does not allow makers or agents to configure `ref` or enable a `ref` alias.
  2. On inbound clicks to `GET /v1/go/:code`, `cleanGoQuery` (`handlers/go_privacy.go:47`) strips `?ref=<source>` before redirect handling, and `inboundViaFromQuery` (`handlers/redirects.go:158`) only inspects `c.Query("via")`.
  3. On outbound redirects to the merchant landing page, `appendViaParam` only sets `?via=<click_id>`, breaking downstream attribution for merchants whose checkout scripts or referral widgets read `?ref=<click_id>`.
- **ORP v0.3 Fix (`spec/architecture.md` §1.2):**
  - **Inbound `/v1/go/:token`:** Preserve and read both `?via=<source>` and `?ref=<source>` (`via` takes precedence if both are present; `ref` is accepted as a first-class alias and recorded into `clicks.source` reflected in `clicks_by_source`).
  - **Outbound Redirect:** Append `?via=<click_id>` by default, and when the offer specifies `ref_param: "ref"` or `ref_alias_enabled: true`, append `?ref=<click_id>` (or both `?via=<click_id>&ref=<click_id>`).

## 4. Additional Protocol Friction Log (Discovered During v0.3 Implementation & Live Testing)

While building the v0.3 specification, JSON schemas, TypeScript SDK, optional adapters, and running `conformance/run.mjs` against the live Go server (`affilio-api`), we logged the following concrete friction points (recorded exclusively in `GAPS.md`):

1. **Friction #1 — The `plugin-ack` Catch-22 on `/v1/go/:code` (Found by Conformance Test #1 `C1-UNIVERSAL-LINK-NO-ADAPTER`):**
   - When we ran Conformance Test #1 (`C1-UNIVERSAL-LINK-NO-ADAPTER`) against the live Go server, we created a publisher via `POST /v1/agent-accounts`, joined a listed offer via `POST /v1/marketplace/offers/:id/join`, prepared/approved/committed a placement, and recorded a valid receipt via `POST /v1/placements/:id/receipt`.
   - Yet when our test clicked `/v1/go/<campaign_code>` and `/v1/go/<placement_id>` with Email, X, and Blog headers, the Go server redirected (`302`) to the plain landing URL **without** `?via=<click_id>`!
   - **Root Cause:** Migration `041_plugin_wait.sql` and `affilio-api/internal/database/attribution.go` set `plugin_wait = 'waiting'` on `commit` and only transition to `placement_counts_as_live` when `POST /v1/placements/:id/plugin-ack` is called with `X-Plugin-Key`. Recording a receipt (`POST /v1/placements/:id/receipt`) does not clear `plugin_wait`. This makes the WordPress plugin mandatory for click attribution in the current Go server — directly violating Spine Principle #1 ("The tracked link/token is the universal adapter; platform adapters are optional helpers, not required for tracking").
2. **Friction #2 — Mid-Task Content Agent Hit 3 Sequential Gates Before Getting a Link (Found by Conformance Test #2 `C2-NO-EMAIL-NO-SIGNUP`):**
   - When simulating a content-writing AI that just finished drafting a developer blog post and wants to offer *"You can monetize this post, want to test it?"*, calling `POST /v1/revenue/preview` returned a matched offer (`preview_only: true`) but no usable `/v1/go/:token` URL. To obtain an actual tracked link, the agent had to (a) call `POST /v1/agent-accounts` with a human `email` and `domain`, (b) pass DNS/HTTPS domain verification (`POST /v1/sites/:id/verify`), and (c) pass human/operator placement approval. Designing `POST /v1/orp/inline-suggest` (`discover` with `mode: "inline_suggest"`) collapses this into **one unauthenticated step** that mints an ephemeral party ID, ephemeral agent key, provisional `/v1/go/:token` URL, and ready-to-paste snippet immediately.
3. **Friction #3 — `/llms.txt` Contradicted `/v1/agent-accounts` Bearer Auth on `/mcp` (Fixed on This Branch):**
   - `ui/landing/src/agents/facts.mjs` (`signInNote`), `ui/landing/public/llms.txt`, and `affilio-wp/admin/build/landing-v9/llms.txt` previously stated: *"This server needs a Google sign-in today... Keys from /v1/agent-accounts work on the REST API only. /mcp needs the Google sign-in."*
   - In reality, `POST /v1/mcp` accepts `X-API-Key` / `X-Maker-Key` / Bearer tokens from `POST /v1/agent-accounts` (verified live in Conformance Check #10 `L2-MCP-TRANSPORT`). Telling LLM agents in `/llms.txt` that `/mcp` requires a browser Google sign-in caused autonomous agents to abort before calling `/mcp`. We updated `facts.mjs`, `facts.test.mjs`, `proof.mjs`, and both `llms.txt` files on this branch.
4. **Friction #4 — `/.well-known/dcp.json` Advertised Legacy `distributoor` / `distributoor-mcp` v0.1 (Fixed on This Branch):**
   - `affilio-api/cmd/server/main.go` returned `"dcp_version": "0.1"`, `"name": "distributoor"`, and `"command": "distributoor-mcp"`. We updated `/.well-known/dcp.json` and added `/.well-known/orp.json` on this branch to return `"orp_version": "0.3.0"`, `"name": "offer-rails"`, and `"command": "offer-rails-mcp"`.
5. **Friction #5 — Payload Field Naming Drift Between Maker & Publisher Endpoints:**
   - Creating a product (`POST /v1/maker/products`) requires `website_url` and `tagline`, whereas `POST /v1/maker/offers` uses `landing_url` and `terms`, and `POST /v1/placements` uses `surface_url` and `copy`. Standardizing around `uri` / `surface_url` and `Creative` (`headline`, `body`, `target_url`, `disclosure_text`) in ORP v0.3 (`schema/common.schema.json`) eliminates agent guessing.
6. **Friction #6 — 140-Character Copy Cap vs. Long-Form Newsletter/Blog/YouTube Placements:**
   - `POST /v1/placements` enforces a hard `copy_length` check of 140 characters (`affilio-api/internal/entry/policy.go`). While 140 characters fits an X post or compact sidebar blurb, it is too restrictive for a newsletter sponsorship paragraph or YouTube description box. In ORP v0.3, `max_chars` is a per-`Space` constraint (`space.constraints.max_chars`) rather than a global 140-character constant.
7. **Friction #7 — Strict Copy Bans (`\bads?\b`) in Public Copy Tests vs. FTC Disclosure Standards:**
   - `affilio-api/internal/handlers/public_copy_test.go` scans all files under `ui/landing`, `affilio-api`, and `affilio-wp` and fails if the standalone word `ad` or `ads` appears. However, on X, Instagram, and TikTok, the FTC's own endorsed short-form disclosure marker is literally `#ad`. Keeping protocol specs/schemas in top-level `/spec`, `/schema`, `/sdk`, and `/adapters` avoided tripping `walkPublicCopy`, while `public_copy_test.go` should scope its regex to marketing copy rather than `#ad` disclosure tokens.

## 5. Deliberate MVP Cuts & Disagreements with Earlier Analyses

### Deliberate Cuts for the "Afternoon Core" (Spine Principle #5)
To ensure any developer or agent framework can implement Offer Rails Protocol v0.3 in a single afternoon:
1. **Cut Mandatory Cryptographic Signatures (`signature` is Optional in Level 1 & 2):** Earlier drafts proposed mandatory Ed25519 JWS signatures on every protocol message. Requiring keypair provisioning before an agent can even suggest an offer mid-task or click a tracked link kills afternoon adoption. In v0.3, unauthenticated 1-step `inline_suggest` + ephemeral Bearer/API keys are sufficient for Level 1 & 2; detached JWS (`EdDSA`/`ES256`) is an optional upgrade for multi-hop relays and `counterparty_attestation`.
2. **Cut Complex Multi-Hop Escrow State Machines from Core:** Rather than baking Stripe Connect / on-chain escrow primitives into the wire protocol, v0.3 treats settlement verification as an outcome signal fed into `receipt` and `reputation`.
3. **Cut Mandatory Platform Plugins:** Any requirement for a WordPress plugin, X OAuth token, or Substack API key to track clicks or verify deals was cut from the core protocol and moved to optional `SpaceAdapter` helpers (`adapters/`).

### Disagreements with Earlier Gap Analyses
1. **Disagreement on "Affiliate-Only" vs. "Universal Online Growth Protocol":**
   - Earlier analyses treated non-affiliate deals (traffic swaps, link exchanges, cross-sells, reposts) as future "Phase 4" side-projects.
   - **Why we disagree (aligned with Victor's 21 Oct 12:26 vision):** Content creators and makers don't just want affiliate commissions — they want **traffic, engagement, monetization, and clients**. By modeling all five deal types (`affiliate`, `cross_sell_upsell`, `link_exchange`, `traffic_swap`, `repost_retweet`) under one unified `offer` → `counter` → `accept` → `receipt` rail with deal-specific verification, Offer Rails replaces GTM bots and cold email across the entire growth stack.
2. **Disagreement on "Adapters as the Foundation of Multi-Platform Support":**
   - Earlier analyses framed multi-platform expansion (X, Newsletters, YouTube) as a matter of building platform adapters first.
   - **Why we disagree:** Platform APIs are brittle, rate-limited, and paywalled. Making the **Universal Tracked Link (`/v1/go/:token`) + 3-mode Verifiable Receipt (`proof_url`, `public_check`, `counterparty_attestation`)** the universal adapter means Offer Rails works on X, Substack, Beehiiv, YouTube, podcasts, and blogs **on Day 1 with zero platform API keys**. Adapters (`adapters/x`, `adapters/newsletter`) are purely optional ergonomics.
3. **Disagreement on "Mandatory Account Signup First" vs. "Mid-Task Ephemeral Inline Suggestion":**
   - Earlier flows required human or agent account registration (`email` + `domain`) before anything actionable could happen.
   - **Why we disagree:** Content-writing AIs (in ChatGPT, Claude, Cursor, Notion, Ghost, Typefully) assist users mid-draft. If the AI has to ask the user for an email address, domain signup, or API key before showing a working monetization/traffic suggestion, conversion drops to near zero. One-step `inline_suggest` with an ephemeral agent key and provisional `/v1/go/:token` link lets the AI offer value inline first and defer payout claiming until value is proven.
