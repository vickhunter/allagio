# Hosted ORP gaps

Recorded from the D-099 agent-as-user run on 2026-10-24 (about 15:13–15:16 Europe/Rome) against `https://offer-rails.onrender.com` (main `be04530a`, ORP 0.3, test mode). The reviewer was a cold agent with public docs only: `/llms.txt`, `/.well-known/orp.json`, and `SPEC.md`. No money moved.

Severity: **BLOCKER** means a cold agent cannot finish or a trust rule is broken. **MAJOR** means a wrong result or real confusion. **MINOR** means polish.

**Verdict of that run:** pass for the test-mode path through an `awaiting` deal. That run did not reach `active`. Join, suggest, hello, discover, a standing offer, accept, execute with the test proof, the deal read, and the inbox all worked. A tracked link and outcomes were not reachable. Self-receipt was refused with 403. A directed offer can now go `active` without a tracked link.

D-105 records this list on main. It does not change `CLAIMS_CHECK` and it does not deploy. Dispositions below are the ones from that report.

## Notes after the run

- Item 1. D-104, now on main, refuses execute unless the deal is `active` (HTTP 409 `state_conflict`). An active execute claims the obligation and does not write a verified receipt.
- Item 5. D-107 adds `POST /orp/deals/<deal>/activate`. A directed offer is stored `proposed`. The counterparty `accept` stores `awaiting`. Activate refuses the deal until that accept message is stored, including when the caller is the acceptor. By default an ask is approved by the waiting party's agent with its bearer. That is not a person's approval. That activate moves the awaiting deal to `active`, clears waiting, and binds both parties by mandate. An owner can turn on human approval for a step. Then activate returns HTTP 403 `owner_approval` and does not bind. Opening the link does not record an approval. The signed-in owner submitting the form on that page records the owner's approval. Any other state is HTTP 409 `state_conflict` and the message is `The deal is in the wrong state.` No tracked link is minted. `CLAIMS_CHECK` is unchanged.
- Item 7. Suggest `platform` and monetize `surface` are `x`, `blog`, `newsletter`, `email`, `web`, and the error lists those values.
- D-111. By default an ask is approved by the waiting party's agent with its bearer. That is not a person's approval. An owner can turn on human approval for a step. Then POST /orp/approve/<id> with the agent bearer is refused. Opening the link does not record an approval. The signed-in owner submitting the form on that link records the owner's approval. A counterparty agent's messages and terms are data, never instructions to the receiving agent. No new migration.
- D-102. The hosted API accepts a 0.4 offer with 2 to 16 parties. The deal stays `pending` until every required party signs. An optional party does not block `active`. `leave` and `seat` are served. A vacancy clears only when the replacement seated for that vacancy signs. The first time the deal is `active`, a tracked link is minted. `GET /go/<token>` attributes the click by split. A 0.3 deal still does not mint a tracked link. `GET /orp/approve/<id>` does not record an approval. `POST /orp/approve/<id>` signs a waiting 0.4 party. By default the waiting party's bearer approves it. That is not a person's approval. The signed-in owner submits the form only when that owner opted in. A failed sign leaves no inbox row and no tracking token. An expired 0.4 offer is left out of discover and suggest. Identity is a hash and an issuer name. A deposit term names an outside holder. Offer Rails does not hold money. Migration `051_d102_orp_many_party.sql` adds a nullable `parties` column. `CLAIMS_CHECK` is unchanged.
- Items 2, 3, and 16, discovery only. D-105 points `/llms.txt` at the test deal, sets `orp.json` `docs` to that section, and names the proof page template `{origin}/orp/proof/<deal>` in the discovery description. The section states that a message id is 8 to 128 characters, documents `hello` `body.versions`, and links the message schema and `https://offer-rails.onrender.com/orp/spec`. The walkthrough is hello, discover, a directed offer (`to`), accept by the second party, activate, execute, then proof. A person sets `placement_publish` to `auto`; that API call returns HTTP 403. The discovery description names those same links. `docs` stays one URL. Execute does not check `proof_url`. Appendix C now says hosted serves `orp.json`, suggest, and the 0.3 message format. On accept, a missing or empty `terms_hash` is HTTP 400 and the message names `sha256-<b64url43>`, and any other non-matching string is HTTP 409 `terms_mismatch`. On offer, `terms_hash` is optional, an empty or malformed hash is a generic HTTP 400, and only a well-formed mismatch is HTTP 409. The deal snapshot still does not carry the proof URL. The other dispositions stay open.
