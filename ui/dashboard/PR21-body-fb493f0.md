## Summary

Backend for D-032 agent entry and the D-031 approval policy, plus the later interface decisions the UI is built against. Additive only. Migrations `018_d032_agent_entry.sql` through `030_d032_ui_wiring.sql`. No deploys. The WordPress plugin that removes and re-inserts the block is not in this PR. There is no push channel; clients poll.

## UI wiring

Head `fb493f0ce242972b8e1c3eaf1a616be059a13b34`. Migration `030_d032_ui_wiring.sql`. Coverage on this revision is 68.9%.

Each digest item on `GET /v1/digest` and `GET /v1/account/digest` includes `plugin_state`, `live_now`, `post_title`, `position`, `link_text`, `label`, `clicks`, `approved_by`, `policy_rule_id`, `policy_rule_text`, and `rules_version`. Placement items also include `plugin_failed_reason` and `failed_action`. An offer item sends `plugin_state` as an empty string and omits `plugin_failed_reason`. `live_now` is the shared `placement_counts_as_live` view for a placement, and true for a listed offer. The digest envelope adds `paused` (`account`, `site`, `offer`), `went_live_since_last`, `change_url`, `site_url`, and `available_modes`. `went_live` stays the current live count. `went_live_since_last` counts placements that count as live and whose live timestamp is after the previous digest open. `change_url` is the dashboard URL (`<base>/owner`) for changing the approval mode or the rules. `site_url` is the site home.

Setup (`GET`/`PUT /v1/setup/settings`) returns the same `change_url` and `site_url`, plus `available_modes` (`manual`, `auto`, `yolo`). It accepts and returns `project_name`, `listing_url`, and `commission` as `{type, value, currency}` with `type` `percent` or `fixed`. `currency` is required when `type` is `fixed`, and a percent may leave it empty. Optional `listing_price` is `{value, currency}` and must use the commission currency when both set one. `commission` and `listing_price` are null when unset. Readiness signals and publisher types to avoid are rejected (400) and wait until after the MVP.

When the claim checker is the stub, setup `mode` is the effective mode: `manual` when the saved or default mode is `yolo` or `auto`, with `approval_reason` `claim_check_unavailable` and `approval_message` `Automatic approval is off until claim checks are live.` `mode_shown` stays what was shown. `mode_preselected` stays the source default. The digest sets `effective_mode` to `manual` with that same `approval_reason` and `approval_message`.

`GET /v1/placements/:id` allows one call every 2 seconds per placement, so a poll every 4 seconds still succeeds. A second call inside the window is 429. A maker project key can `GET` the status and the placement read for a placement on its own offer. Another offer is 403. Retry stays publisher-only and returns 403 for a maker.

Restoring or redoing a placement that was not undone is `POST /v1/placements/:id/restore` and returns 409 `{reason: not_undone, message: The placement was not undone.}`. Undoing a listing is the existing `POST /v1/digest/undo`, which pauses the offer. The parity row is `Undo a listing (no redo in v1)`. There is no listing redo route in v1.

`GET /v1/policy/hard-checks` is the single source the UI renders. The response is `{checks:[{check_id, check_text}]}` from `HardCheckCatalog`, in that order.

Maker commission on `GET /v1/maker/earnings` is `offers[].commission` with `offers[].currency`, and `totals[].commission` with `totals[].currency` and `totals[].mode`. On `GET /v1/account/digest`, maker commission is the offer project's `earnings` list of `{currency, amount}` (`projects[].earnings`). Publisher income is `totals.earnings`, the same `{currency, amount}` list, and it does not include maker commission. `earnings` is null when that scope has no test-mode rows.

## Interface the UI uses

1. Approvals return `policy_rule_id` (`hard_checks_passed` or `category:invoicing`) and `policy_rule_text`, a sentence the server writes.
2. Undo is `POST /v1/placements/:id/revoke` with `{"reason":"undo"}`. It takes effect in that request in the API and in MCP. There is no delay. That records a `placement_undo` event. When the placement is `failed` with `failed_action` `restored`, that same undo sets `plugin_state` to `pending`, clears `failed_action`, stops the go link, and leaves the placement out of Live now. It becomes `removed` only on a verified plugin acknowledgement `action: removed`, `offline` after 10 minutes with no acknowledgement, or `failed` with `failed_action` `removed` on a failed acknowledgement. Digest totals, site totals, and Live now exclude that failed restore. `placed` and `removed` are stored only by that verified plugin acknowledgement. Revoke, restore, retry, pause, and the kill switch do not set them.
3. `POST /v1/placements/:id/restore` applies only to that placement id, and only within 6 seconds of its server undo timestamp. After that it returns 409 `{"reason":"window_expired","message":"The restore window has expired."}`. Only the same user and key identity that undid it may call it. Anyone else, including the other side, gets 403. If Pause or the kill switch was turned on for that site, offer, or account at any point after the undo, including when it is still on, restore returns 409 `{"reason":"paused","message":"Pause or the kill switch was turned on after the undo."}`. Every 409 returns `{reason, message}`, and `message` is the plain-English text from `RestoreRefusals`. Every 422 returns `{check_id, check_text}`. `/llms.txt` and `/docs/modes.md` render that enum the same way they render the hard checks. The server re-runs every hard check. Relevance is scored on the server from the approved copy and the offer. rel=sponsored comes from that copy and the disclosure. The current 30-day cap and the current minimum relevance are checked again, and pause and the cap are checked in the same transaction as the restore update. A failing check returns 422 `{check_id, check_text}` and leaves the placement revoked. Success restores the pre-undo status, keeps `approved_by`, sets `restored_by`, and records a `placement_restore` event. After a successful restore, `plugin_state` is `pending` until the site key acknowledges it.
4. The same revoke is allowed for the site owner or the offer's maker. `revoked_by_side` is `publisher` or `maker`.
5. `POST /v1/account/pause` takes `{"scope":"all"|"site"|"offer","id?"}`. The server sets manual mode on every site and offer in that scope and pauses unpublished policy approvals. An account key or a session may pause. A project key is limited to the agent route allow-list. `POST /v1/account/resume` uses the same body and is session-only (403 with any key).
6. `earnings` is a list of `{currency, amount}`. The list is null when that scope has no test-mode rows, and it includes a zero amount when the recorded rows add up to zero. Publisher income does not include maker commission. Maker amounts stay on the offer.
7. Setup and digest payloads include `session: {signed_in: bool}`. Setup also includes `human_login`.
8. Setup includes `mode_preselected`, derived by the server from `owners.source`. `cli`, `cursor`, `grok`, and `mcp` preselect yolo. Every other source preselects manual. A query `install_path` does not select the mode.
9. `GET /v1/go/<placement_id>` always returns 302, including for an unknown id, and never a 404 or a 5xx page. A ref is attached and a hit is recorded only when `placement_counts_as_live` is true. Revoked, pending undo, paused (`all`, `site`, or `offer`), kill switch, offline, failed, and removed placements redirect to the offer's plain URL with no ref and no hit. When the offer itself is not live, the redirect is the placement `post_url`, or the site home when `post_url` is missing. An unknown id redirects to the site home when `?via=plugin` carries that site's key, and otherwise to the Offer Rails home page. Every go-link response, tracked or not, sends `Cache-Control: no-store` and `X-Robots-Tag: noindex, nofollow`. `GET /v1/go/<placement_id>?via=plugin` with `X-API-Key` accepts `X-OR-Client-Hash`, `X-OR-User-Agent`, and `X-OR-Referer` for hit dedup and bot filtering, and only when that key matches the placement's site. `X-OR-Client-Hash` is the lowercase hex HMAC-SHA256 of the truncated address (`/24` for IPv4, `/48` for IPv6), keyed by the daily salt that rotates at 00:00 UTC. Dedup uses that hash plus the user agent, scoped to the site. Without a matching site key those headers are ignored and the connection address is truncated and hashed in memory with a server salt from `API_KEY_SECRET` that rotates at 00:00 UTC. The raw address is never stored and is scrubbed from request logs, access logs, and error reports. Do not send `X-OR-Client-IP`. The placement payload includes `fallback_url`, the plain offer URL. The old campaign route `GET /v1/go/<code>` stays supported permanently and never returns a 4xx or a 5xx. `?placement=` follows the placement rules. Without that query, a hit is recorded only when a placement on the campaign's site counts as live. Every other resolved code redirects to the offer's plain URL with no ref and no hit. When the offer is not live, a bare code redirects to the site home. An unknown code redirects to the Offer Rails home page. A rate limit is that untracked 302, never a 429.
10. Every placement in `GET /v1/digest`, `GET /v1/account/digest`, and `GET /v1/placements/:id` includes `plugin_state`. It is never null. The only values are `pending`, `placed`, `removed`, `offline`, and `failed`. A brand-new placement is `pending` until the site key's first `POST /v1/placements/:id/plugin-ack` with `{"action":"restored"}`, which sets `placed`. After a restore it is `pending` again until that same acknowledgement. After a revoke it is `pending`, then `removed` on `{"action":"removed"}`, or `offline` after `PLUGIN_OFFLINE_AFTER` (default 10 minutes) with no acknowledgement. `offline` is only that missing acknowledgement. `{"action":"failed","reason"}` stores `plugin_failed_reason` and `failed_action` (`removed` or `restored`) and sets `plugin_state` to `failed`. Retry repeats only that action. A later verified acknowledgement for the same action clears the failure. Placement reads and both digests include `plugin_failed_reason` and `failed_action`. Offers do not get those fields. A poll does not change the state.
11. A 422 from restore, retry, decide, or publisher accept is `{"check_id","check_text"}`. `check_id` is one of `disclosure`, `rel_sponsored`, `claims_from_offer`, `copy_length`, `one_per_post`, `relevance_min`, `offer_live`, `revoke_path`, `cap`. That list and its text live in `HardCheckCatalog`. `/llms.txt` and `/docs/modes.md` render the section from that catalog. `GET /v1/policy/hard-checks` returns the same pairs. When more than one check fails, the body is the earliest id in that order.
12. There is no push channel. Clients poll `GET /v1/placements/:id`. The read selects `status`, `plugin_wait`, `plugin_wait_at`, `plugin_failed_reason`, and `failed_action` from `placement_proposals` by primary key and does not join another table. The rate limit allows one request every 2 seconds per placement, so a poll every 4 seconds still succeeds.

## What the plugin calls later

This PR does not change the WordPress plugin. The merged plugin should poll; nothing is pushed.

- A brand-new placement is `pending`. When the block is in the post, `POST /v1/placements/:id/plugin-ack` with the site key and `{"action":"restored"}`. The state becomes `placed`. That call does not create a post revision.
- After an undo, `plugin_state` is `pending`. Remove the block with no post revision, then the same endpoint with `{"action":"removed"}`. If that acknowledgement does not arrive within 10 minutes, the state becomes `offline`. A later `removed` acknowledgement still moves `offline` to `removed`.
- After a restore, `plugin_state` is `pending`. Re-insert the block with no post revision, then `{"action":"restored"}`. The state becomes `placed`.
- If the post re-read still fails after one retry, call `plugin-ack` with `{"action":"failed","reason":"..."}`. `plugin_state` becomes `failed` and `plugin_failed_reason` stores that reason. `offline` stays the 10-minute outcome of no acknowledgement. A later verified `removed` or `restored` acknowledgement for the pending action clears the failure.
- The publisher retries with `POST /v1/placements/:id/retry`, using the owner session or the site key. The other side receives 403. Retry repeats only `failed_action`. Any other state returns 409 `{reason: not_failed, message}`. A failed removal re-queues only the removal: `pending`, then `removed`. It does not re-run hard checks, it does not become `placed`, and the go link stays stopped. A failed restore re-runs every hard check. A failure returns 422 `{check_id, check_text}` and leaves the placement failed. Success re-queues the restore: `pending`, then `placed`. A failed restore is not live: the go link stops, and digest totals, site totals, and Live now exclude it, including the went-live count and earnings from its clicks, until a verified `restored` acknowledgement sets `placed`.
- Leave a failed restore removed with the same undo. `plugin_state` becomes `pending` in that request, `failed_action` is cleared, the go link stops, and the placement does not count as live. It becomes `removed` only on `{"action":"removed"}`, `offline` after 10 minutes with no acknowledgement, or `failed` with `failed_action` `removed` on `{"action":"failed","reason":"..."}`. `placed` and `removed` are stored only by that verified plugin acknowledgement. Revoke, restore, retry, pause, and the kill switch do not set them. Removing the block does not create a post revision.
- Poll `GET /v1/placements/:id` for `status`, `plugin_state`, `plugin_failed_reason`, `failed_action`, and `fallback_url`. One request every 2 seconds per placement is allowed, so a poll every 4 seconds still succeeds. A maker project key can read its own offer. Retry stays publisher-only. `fallback_url` is the offer's plain URL, so the plugin can cache it. The status SQL stays a single-table read; `fallback_url` is a second query.
- The merged plugin will serve `/go/<placement_id>` on the publisher site, call `GET /v1/go/<placement_id>?via=plugin` with the site key and a 1.5 second timeout, without following redirects, and forward the `Location`. This PR does not add that WordPress proxy. Send `X-OR-Client-Hash`, `X-OR-User-Agent`, and `X-OR-Referer`. The hash is the lowercase hex HMAC-SHA256 of the truncated reader address (`/24` for IPv4, `/48` for IPv6), keyed by a per-site salt that rotates at 00:00 UTC. The salt is the lowercase hex SHA-256 of `siteSecret + "|go-link|" + YYYY-MM-DD`. Those headers count only when the key matches the placement's site. Do not send the raw address.

## Live count

A placement counts as live only when both are true: `plugin_state` is `placed`, and its go link is currently redirecting. `placed` is stored only by a verified plugin acknowledgement. The go link is redirecting when the placement is still committed, not expired, the offer is listed, the campaign is active, Pause is off for that site and that offer, and the kill switch is off. Pending, failed, offline, removed, paused (`all`, `site`, and `offer`), kill switch, and revoked-but-plugin-still-placed placements are out of the count. Live now, site totals, digest went-live, and account totals all use the `placement_counts_as_live` view. Listed offers are not placements. Digest totals, site totals, and Live now still exclude a failed restore, including earnings from its clicks, until a verified `restored` acknowledgement. Tests: `TestPlacementLiveCountExclusions`.
